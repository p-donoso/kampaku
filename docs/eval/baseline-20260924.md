### Found after run 5: every run in this record was measured through a truncated turn

This is the largest finding in the document, and it invalidates the *reasoning* behind several earlier
results while leaving their *observations* intact.

Prompted by a question about whether the endpoint was choosing weak models, the endpoint's own
configuration was inspected. It is not a model choice. It is a context limit:

```text
$ ps -ef | grep llama-server
root  1016915 ... /snap/ollama/137/lib/ollama/llama-server \
  --model ... --port 34869 --no-webui --offline \
  -c 4096 -np 1 --log-verbosity 4 --no-jinja --chat-template chatml \
  --flash-attn auto -b 512 -ub 512 --context-shift --keep 4

$ ollama ps
NAME           SIZE      PROCESSOR       CONTEXT
qwen2.5:14b    10.0 GB   16%/84% CPU/GPU 4096

$ ollama show qwen2.5:14b | grep -i context
    context length      32768      # the model supports 32k
```

`-c 4096` is the server's context. `--context-shift` means that when the context fills, the server
**discards the oldest tokens and continues** instead of failing. Nothing surfaces in the API response,
the CLI output, or the logs. The model supports 32 768 tokens and is being run at 4 096.

**Measured, not inferred.** Sending increasingly long prompts and reading `prompt_eval_count`:

| Filler words | `prompt_eval_count` | Looked for a marker at the START of the prompt |
|---|---|---|
| 300 | 1 266 | **found** |
| 900 | 3 622 | **found** |
| 1 500 | **2 050** | **gone** |
| 2 500 | **2 050** | **gone** |
| 4 000 | **2 050** | **gone** |

Below the limit the model retrieves the fact. Above it, the prompt is cut to a constant and the start is
lost. The cap scales with `num_ctx`, which proves it is the limit and not the model: 4 096 → 2 050;
8 192 → 4 098; 16 384 → 8 194 (always the effective limit minus roughly the reply budget).

**And the turn does not fit.** Measured on the real artifacts — the builtin orchestrator prompt plus the
operator skills, exactly as `session.ts` assembles them against the run-5 data dir:

```text
system prompt chars:                              19 984
prompt_eval_count for the REAL system prompt:      4 086
server context:                                    4 096
```

The system prompt **alone** consumes 4 086 of 4 096 tokens. The durable-state block, the history, and
the operator's question are then dropped from the front by `--context-shift`. Every turn in this record
ran that way.

**A consequence worth stating plainly: a 4 000-token context means the front office's own identity
paragraph is a few hundred tokens away from being dropped.** The system prompt is assembled as
global-prompt + builtin-definition + skills, and truncation removes from the front — so the earliest
content is the most fragile. That is the opposite of what a prompt is written for, and it may matter more
than any wording.

### This is an environment defect and a product gap, and they are different

The endpoint is misconfigured for this workload. That is an **operator/environment** finding, and the
fix is a server setting (`OLLAMA_CONTEXT_LENGTH`, or `num_ctx` per request), not a code change in this
repository.

The **product** gap is separate and worse: Kampaku sent a 10 000-token prompt to a 4 096-token endpoint
and had **no way to notice**. Requirements that follow, and they are [F-008](results/BOARD.md)'s stated
rule — *capability must be negotiated and verified per endpoint, and a tool-incapable or too-small model
must be detected and reported as an endpoint gap* — applied to context rather than to tools:

1. Discover the effective context at startup and **fail loudly** when the assembled turn does not fit,
   rather than sending a truncated turn and scoring the reply.
2. Never let a truncating endpoint silently satisfy a suite. A run that could not fit its own prompt is
   not a measurement of the product.
3. Report the effective context wherever the model is reported, the way the CLI already reports
   `mode: llm · model: qwen2.5:14b`.

Recorded as **[F-032](results/BOARD.md)**, owned by [roadmap 11](../roadmap/11-multi-provider-routing.md)
§ Part A, which is the same deliverable that already owns endpoint capability negotiation.

### And it is why the repetition plan below matters more, not less

Fixing the context does not retire the sampling problem. It makes it measurable: until the turn fits,
nothing about this endpoint's behaviour can be attributed to anything.

### How a fourth run should be taken

The recipe is unchanged, and it is the same one run 3 used:

```bash

node apps/core/dist/cli.js bootstrap
node apps/core/dist/cli.js serve &          # Core on 127.0.0.1:18080

# 3. The four suite-01 prompts, in order, recording each.
#    Prompt 1 must name the project and the team. Prompt 4 must read state, not ask for a name.
```

The oracle is `~/.kampaku-eval-01/oracle.py` (documented REST only). The four prompts are in
[suite 01](01-work-order-intake.md) § Emperor prompts.

**Traps that cost time in runs 1–3 and are not product defects:**

1. The repository's own `.env` sets `KAMPAKU_CORE_URL=http://127.0.0.1:8080`. Setting only
   `KAMPAKU_CORE_PORT` leaves that value in force, and the CLI then reports *"Core is not running"*
   against a healthy Core. `run.env` sets `KAMPAKU_CORE_URL` explicitly.
2. Do not run `npm test` in parallel with anything else. Two worker tests shell out and hold vitest's
   5 s default; on a loaded host they fail and it looks like a product defect. This is
   [F-020](results/BOARD.md). Runs 1–2 hit it once each from exactly this cause.
3. **New in run 3: one prompt at a time.** A turn takes 60–90 s on this endpoint and the CLI streams to
   the terminal. Chaining prompts in one shell invocation loses the earlier output, and the run has to
   be repeated. Redirect each prompt to its own file and wait for the process to exit.
4. **New in run 3: do not poll a process id you did not just receive.** Four turns were spent calling
   `get_process_status` with a guessed id, each returning 404. The id is in the response.

### F-024 — Inspection answers from memory and contradicts durable state

*Re-measured in run 3 (§ Run 3 above): the reply is no longer invented and no longer from recollection,
and it still does not answer the question. Three runs, three different shapes, no pass.*

`tools: none`. Asked what exists, the front office called no tool and described an empty instance while
one project and nine agents existed. In a second run it invented a five-role roster
(`kampaku-lead`, `-frontend`, `-backend`, `-qa`, `-auditor`) that does not match the nine real agents,
three of which do not exist at all.

The durable-state block was correct — it listed `kampaku [active] lead=… repositories=4 workItems=0` —
and the reply contradicted it anyway. The block states its own precedence and tells the agent to call a
tool rather than answer from memory; nothing enforces either.

This is the [F-014](results/BOARD.md) family, which the board already describes as reconciliation
covering *creation* claims but not misstated *state*.

**Diagnosis: the failure is steering, not capability.** Two controls settled it.

| Prompt | Tool calls | Answer |
|--------|-----------|--------|
| `what exists here — projects, teams, open work?` | **none** | empty instance; then an invented five-role roster |
| `Use the list_agents tool, then tell me the exact agent slugs it returned.` | **`list_agents`** | correct and in English: the eight real platform sub-agents |

So the model can call tools on this endpoint, and it reads state correctly when it does. What it does
not do is decide, on its own, that a question about the factory's own state requires reading state.
And the language question falls with it: the same model answered an English prompt in English as soon as
it had a tool result to report, which points at the reply being generated from a weak prior rather than
from retrieved state.

That reframes the fix. F-024 is not "the endpoint cannot call tools" (F-008's shape) and not "the model
is too weak". It is that **an inventory question has no enforced route to an answer**: the durable-state
block omits the roster (F-025), and the instruction to call a tool is unenforced prose.

### F-025 — The durable-state block has no agents or teams

It lists projects, pending questions, and blockers. An operator asking "what teams exist" has no

### F-026 — Stored provider settings silently outrank the environment

`resolveModelProviderSettings` returns `store.getBootstrapState(SETTINGS_KEY)` in preference to
`config`. The provider settings written at bootstrap therefore pin the model, and changing
`KAMPAKU_AGENT_MODEL` afterwards has no effect — verified directly:

```text
env:        KAMPAKU_AGENT_MODEL=qwen2.5:7b-instruct   → loadConfig().agentModel = qwen2.5:7b-instruct
stored:     GET /api/v1/settings/model-provider       → model: qwen2.5:14b
the turn:   mode: llm · model: qwen2.5:14b            ← the stored value won
```

An operator who changes the endpoint or model in the environment and sees no change has no signal
telling them why. This is the same shape as the `KAMPAKU_CORE_URL` surprise, and it is what
[roadmap 11](../roadmap/11-multi-provider-routing.md) § Part A means by *documented precedence*.

## Operator defects

The protocol requires the operator's own mistakes in the ledger. They cost real time here:

1. **A `pkill` pattern matched the operator's own shell.** `pkill -f "dist/cli.js serve"` killed the
   command that contained that string, so a wipe-and-restart silently half-ran and the next bootstrap
   reported "Project already exists". Recovery: verify the port is free instead of killing by pattern.
2. **Two env names for one setting.** Setting `KAMPAKU_CORE_PORT` while the repo's `.env` set
   `KAMPAKU_CORE_URL` produced a CLI that reported "Core is not running" against a Core that was
   healthy. The CLI reads the URL.
3. **An empty workspace root produced a false gap.** The first bootstrap linked non-existent
   repository paths because the workspace pointed at an empty directory, not because the product is
   broken. Corrected before being reported, by re-running with the documented value.
4. **Device-brace expansion does not run in a non-interactive shell**, so a `mkdir -p a/{b,c}` created a
   literal directory named `{b,c}`. Cosmetic, but it is a reminder that the run is scripted.

   ### The block is lossy in exactly the fields that were asked for

   This is what makes (a) a specification rather than a preference. The durable-state block is the source
   the prompt tells the agent to answer from, and here is what it renders for the container prompt 4 was

   | Asked for | In the block | Reachable over REST |
   |---|---|---|

   obeyed the block perfectly would still have failed prompt 4, and no prompt work can fix that, because
   the answer is not in the source the prompt points at.
