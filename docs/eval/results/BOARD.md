# Eval board (product gaps)

Open gaps found while running the `docs/eval` lab. Language is **product gap**, not catalog patch.

Rows are opened from three sources: a suite run, a capability probe
([capability-probe-protocol.md](../capability-probe-protocol.md)), or a direct contradiction found by
reading the product's own artifacts. A row exists only for a **measured** gap — an unverified
capability is listed under *Unverified capabilities* below, not here.

## Status legend

- `open` — blocks or fails a suite
- `in_progress` — a change owns the fix
- `resolved` — fixed; suite re-run on a fresh data dir still required before calling the suite green
- `wontfix` — accepted debt; the suite stays failed until the bar changes with emperor approval

## A row is a summary, not a record

This board answers one question: **what is broken, how badly, and where do I read the rest.** It is not
where a measurement, a transcript, or a fix narrative lives.

- **An `open` row's detail is its GitHub issue**, linked from `notes`. The issue holds the specimen, the
  commands, the job or gate ids, and the required behaviour in full.
- **A `resolved` row's detail is its commit and its suite document.** The text a resolved row carried
  before 2026-11-23 is two commands away, both verified on `F-053`: `git log -S "F-0NN" --oneline --
  docs/eval/results/BOARD.md` names the commit that reduced the row, and
  `git show <commit>^:docs/eval/results/BOARD.md` prints the board as it stood before it — the old row,
  verbatim, including the measurements the new one summarises.
- **The budget is enforced, not asked for:** a row is at most 700 characters, `symptom` and `product gap`
  are one sentence each, and `notes` is a pointer. `npm run check:docs` fails a board that exceeds it, and
  also fails an `open` row with no issue, or a duplicate id.
- **New detail goes to the issue (or the suite's `.md`) first.** A row then gains the one sentence that
  changes its verdict — never the reasoning that produced it, and never a re-measurement log.

## Dependency rule

Do not start suite **N** if an `open` row marked as blocking that path exists for a suite earlier in
the order. The former arc entry blocker F-001 is resolved, so the battery can start at suite **01**
([ADR-0005](../../adr/0005-factory-authority-model.md)).

## How to add a row

1. `id`: `F-NNN`, continuing from the highest existing number — and check it is free, because two pairs of
   rows once shared an id (`check:docs` now refuses a duplicate).
2. `suites`: which suites the gap blocks or fails.
3. `symptom`: one sentence — what the operator saw, with the one piece of evidence that makes it a fact.
4. `product gap`: one sentence — what a credible factory would do instead.
5. `likely layer`: core / worker / web / contracts / scripts / docs — not a skill slug.
6. `owner`: the ADR, roadmap deliverable, or current product document that owns the fix.
7. `status`: see the legend.
8. `notes`: the issue number for an `open` row. For a `resolved` row, the date, the commit or PR, and a lock
   if one exists.

Open the issue first and put the measurement in it: the specimen, the commands, the ids, the transcript
paths. Then write the row. A gap that only exists in a probe's ledger is not yet a row — promote it when it
blocks a suite or when a suite is written for it.
